\section{Results and Discussion}
\label{sec:results}

This section presents the experimental evaluation of our extended QuantumC compiler. We first describe the experimental setup and benchmark suite, then analyze the compilation results for vector and matrix operations. We compare the two arithmetic backends (QFT-based and ripple-carry) and demonstrate the effectiveness of our compile-time sparsity optimization, which reduces circuit complexity when input matrices contain zero elements.

\subsection{Experimental Setup}
\label{sec:setup}
We evaluate the extended QuantumC compiler using the following configuration. The C source programs are parsed using Clang~\cite{clang} to produce JSON abstract syntax trees. The MLIR generation and dialect definitions rely on xDSL~\cite{xdsl}, a Python-native compiler toolkit that supports progressive lowering. The resulting quantum circuits are synthesized and validated using the Qiskit SDK~\cite{qiskit}. All experiments were executed on a MacBook Pro equipped with an Apple M3 Pro chip (11 cores) and 18\,GB of RAM, running macOS with Python 3.12.

The benchmark suite consists of five representative programs that exercise the extended compilation capabilities: two vector addition programs with different sizes ($N=2$ and $N=4$), a dot product computation, a $2 \times 2$ matrix multiplication, and a hybrid program combining scalar arithmetic with vector operations. All benchmarks use 4-bit integer representation, except for matrix multiplication which requires 8 bits to accommodate the range of computed values.

\textbf{Benefits of pattern-based recognition.} The comparison between vector addition at $N=2$ and $N=4$ highlights a key advantage of our pattern-based approach. While qubit count and gate count scale linearly with vector size (doubling from 36 to 68 qubits and from 357 to 710 gates), the circuit depth remains constant at 84. This is possible because our compiler recognizes vector addition as a single high-level operation, rather than treating it as a sequence of independent scalar additions.

In a vector addition $c[i] = a[i] + b[i]$, each element computation is independent from the others: computing $c[0]$ does not require the result of $c[1]$, and vice versa. By capturing this semantic information at the pattern recognition stage, the compiler can generate $N$ parallel addition circuits that execute simultaneously, keeping the depth equal to that of a single addition. A naive approach based on loop unrolling would instead process each iteration sequentially, resulting in a depth that grows linearly with $N$. The pattern-based approach thus preserves the inherent parallelism of vector operations~\cite{hls-book}, which is essential for generating efficient quantum circuits. Figure~\ref{fig:circuit} shows the quantum circuit generated for the vector addition kernel \texttt{c[i] = a[i] + b[i]}. The compiler allocates separate quantum registers for input vectors (\texttt{a}, \texttt{b}) and output vector (\texttt{c}), preserving reversibility. Each element-wise addition uses the QFT-based arithmetic backend described in Section~\ref{sec:quantum-arithmetic}: the repeated QFT and inverse-QFT blocks visible in the circuit correspond to independent additions performed for each vector element.

\textbf{Cost of multiplication-based operations.} The dot product and matrix multiplication benchmarks show significantly higher circuit depth: 650 for dot product versus 84 for vector addition of the same size. This difference has a simple explanation: these operations require accumulation into a shared result.

In vector addition, each output element $c[i]$ is computed independently. In contrast, the dot product $s = \sum_{i} a[i] \cdot b[i]$ accumulates all partial products into a single scalar $s$. Each accumulation step must wait for the previous one to complete before updating $s$, creating a sequential chain that cannot be parallelized. Matrix multiplication exhibits the same pattern: each output element $C[i][j]$ requires $K$ sequential multiply-accumulate operations. Additionally, multiplication itself is more expensive than addition in quantum arithmetic, further increasing both depth and gate count.

\textbf{Hybrid compilation.} The hybrid benchmark validates the merge phase of our extended pipeline. This benchmark contains both scalar arithmetic (compiled through the standard QuantumC path) and a vector addition (compiled through our extended path). The two paths are compiled independently and then merged into a unified quantum circuit.

The resulting circuit (44 qubits, depth 84) is only slightly larger than the pure vector addition (36 qubits), with the additional qubits allocated for scalar variables. The constant depth confirms that the merge phase correctly combines the two paths without introducing unnecessary dependencies. The \emph{result map} plays a crucial role in this process: when the C program returns a vector element such as \texttt{c[2]}, the compiler uses the result map to locate the corresponding quantum register and connect it to the output measurement, ensuring correctness even though scalar and vector computations were handled separately.

\subsection{Arithmetic Backend Comparison}
\label{sec:backend-comparison}

Table~\ref{tab:results} enables direct comparison between the two arithmetic backends. The results reveal that, when using a uniform gate set, the ripple-carry backend produces more compact circuits in terms of total gate count and CX gates, while the QFT backend requires fewer qubits.

For addition-only workloads (vec\_add and hybrid), ripple-carry circuits use fewer CX gates (108 vs 128 for $N=2$) and fewer total gates (261 vs 357). The QFT backend, however, maintains an advantage in qubit count (36 vs 38) and circuit depth (84 vs 92). This difference arises from the algorithmic structure: QFT-based addition operates in the Fourier basis using controlled phase rotations, which are decomposed into multiple CX gates when transpiled to a uniform gate set. Ripple-carry addition uses explicit carry propagation with Toffoli gates, which decompose more efficiently.

For multiplication-based operations (vec\_dot, matmul), the situation is similar. Both backends require high CX counts due to the shift-and-add multiplication algorithm, where each partial product addition must be conditionally executed. The ripple-carry backend maintains its advantage in gate count (1713 vs 1797 for vec\_dot), while QFT retains lower qubit requirements (40 vs 42) and depth (650 vs 726).

The choice between backends depends on the optimization target and hardware constraints. When minimizing qubit count is critical, QFT-based arithmetic is preferable. When minimizing gate count or CX operations is the priority, ripple-carry provides better results.

\subsection{Sparsity Optimization}
\label{sec:sparsity}

\input{figures/sparsity-graphs}

Many real-world linear algebra workloads involve sparse matrices, where a significant fraction of elements are zero. Our compiler exploits this property through a compile-time sparsity optimization: when lowering matrix multiplication from VecMat IR to quantum operations, the compiler checks the constant array values and skips the generation of multiply-accumulate operations for which either operand is zero. Since $0 \times x = 0$ and $\mathit{acc} + 0 = \mathit{acc}$, these operations have no effect on the result and can be safely eliminated.

Figure~\ref{fig:sparsity} shows the impact of this optimization on $4 \times 4$ matrix multiplication with 8-bit integers. We vary the sparsity level from 0\% (dense matrices) to 75\% (12 out of 16 elements are zero) and measure the resulting circuit metrics for both arithmetic backends.

The results demonstrate substantial reductions across all metrics. At 75\% sparsity, qubit count decreases by 68\% (from 1,408 to 448 for QFT), gate count by 94\% (from 37,686 to 2,366), and circuit depth by 72\% (from 1,973 to 552). The optimization is equally effective for both backends, as it operates at the VecMat IR level before the arithmetic backend is selected.

This optimization is particularly valuable for quantum machine learning applications, where weight matrices are often pruned to reduce computational cost. By performing sparsity analysis at compile time, the optimization incurs no runtime overhead and produces circuits that are proportionally smaller to the actual non-zero computation required.
